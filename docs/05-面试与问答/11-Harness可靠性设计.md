# Harness 可靠性设计

> 面试短答：“稳定性来自三道独立控制。第一道把模型输出当候选，来源和工程规则通过才计价。第二道把草案、版本和审批绑定，改量或换图需要重新批准。第三道把同步请求持久化，派发遇到结果不明先查目标，只有读回内容匹配才显示成功。我们用冻结样例和故障注入测试了这些分支。”

当前系统的 Harness 包含两部分。**运行时**由任务状态机、证据校验、版本控制和集成出站队列共同约束识别、计价和写入。**验证时**由固定输入、可控时钟、模拟外部系统和故障注入覆盖正常路径及故障窗口。Agent 的三条任务路径见 [[docs/05-面试与问答/10-AI-Agent设计与实现]]。

## 1. 可靠性来自哪里

| 容易发生的错误 | 系统依赖的保证 | 操作员能看到的结果 |
|---|---|---|
| 模型捏造材料、引用错页、把 A 当 B | 固定输出契约，当前任务来源校验，业务规则与人工复核独立执行 | 缺项、歧义或版次冲突暂停，工程师能回到原件 |
| 两个页面同时改任务，旧请求覆盖新内容 | SQLite 事务、`expected_version` 与版本推进。重要状态和对应审计一起提交 | 过期操作返回冲突，刷新到最新任务 |
| 识别超时或进程中断，任务一直占用 | 先持久化识别尝试和租约，事务外调用识别器，按版本提交结果。超时分类、限制重试、到期可恢复 | 任务可重试或更换识别方式，有可追溯的尝试和错误码 |
| 用 100 件的审批发送 500 件，或用失效费率继续发 | 当前输入、受控参考依据、批准草案哈希和上游来源快照共同约束派发。修改输入使当前派生结果失效 | 重算与重审，旧出站记录保留为历史 |
| ERP 已经保存，客户端却超时 | 出站意图先落库。稳定的业务键和幂等键、按键查询、目标版本检查 | 先显示「结果待确认」，查到已提交记录后再对账 |
| ERP 回执成功，实际金额不同或同一任务有重复记录 | 按业务键检查目标记录数量，读回目标内容并和原始载荷比较 | `MATCH` 才显示「对账通过」。差异、缺失或重复进入处理状态 |

## 2. 任务状态、并发与识别恢复

### 2.1 任务状态和审计一起保存

任务在 SQLite 中保存当前版本和审计事件。写入用 `BEGIN IMMEDIATE`，核对调用方的 `expected_version` 后才推进。界面同时打开两份相同版本时，先成功的一次会推进版本，后续旧版本操作收到 `VERSION_CONFLICT`。任务修改、计价、批准、导出都有相应审计事件。

文件型任务的输入哈希关联当前工程输入、字段和文档哈希。草案还记录受控依据哈希、草案版本和来源快照。审批绑定整份草案哈希。服务端在生成导出和下载时核对当前审批与草案。数量修改会清除当前草案、审批和导出，已生成的历史记录仍可审计。实现见 [持久化与审计](../../apps/api/src/rfq_workbench/repository.py)、[报价与审批](../../apps/api/src/rfq_workbench/service.py)。

### 2.2 识别失败如何恢复

1. 发起识别时，先记录附件组合哈希、识别模式、次数、任务版本和租约期限，状态进入 `EXTRACTING`。同一附件组合及模式最多连续尝试三次，成功后清除该模式的失败预算。不可重试错误可以提前结束该模式的尝试。
2. 模型调用在数据库事务外执行。完成时用领取后的版本提交结构化字段、证据和审计。旧的识别结果不能覆盖已经恢复或更新的任务。配置的在线 SDK 重试为 0，由工作台追踪尝试。
3. 超时、连接异常、限流和部分服务端故障按错误码归为可重试，并受次数约束。超出预算或遇到不可重试的配置、鉴权等问题，工作台保留错误记录，操作员可修正配置、换模式或更新资料。
4. 进程退出导致任务停在 `EXTRACTING` 时，可在租约到期后调用恢复操作，记录 `EXTRACTION_INTERRUPTED`，再根据剩余预算继续。当前租约计算为 `4 × model_timeout + 30 秒`。如果旧调用晚到，版本检查会拒绝它的写入。

实现见 [识别领取、提交和恢复](../../apps/api/src/rfq_workbench/file_workflow.py)、[模型适配](../../apps/api/src/rfq_workbench/extraction.py)。

## 3. 集成 Harness 从依据读取到目标对账

![[docs/04-项目介绍与展示/10-展示附件/06-模拟ERP同步流程.png]]

### 3.1 先固定上游依据

当前上游通过端口读取三类模拟数据，分别是 **PLM 已发布版次、ERP 材料与费率依据、MES 工时反馈**。快照含来源标识和版本、数据时点、获取时间、TTL、映射版本、规范化载荷和哈希。计价会检查 PLM 版次与图纸是否一致、ERP 成本依据是否匹配受控配置。MES 反馈随草案保留，当前费率与模板不会由反馈自动改写。审批与同步会探测来源版本和有效期。默认 TTL 为 **900 秒**，可配置。

当前可映射工厂为 `DE-DEMO`，币种 EUR、尺寸 mm、数量单位 piece。`erp-draft-v1` 把已批准的报价转换为固定字段，金额用两位小数的字符串，核对明细舍入与总价一致性。客户订单、正式报价和实际 ERP 连接处于后续接入范围。见 [来源快照](../../apps/api/src/rfq_workbench/integrations/snapshots.py)、[出站映射](../../apps/api/src/rfq_workbench/integrations/mappers.py)、[集成端口](../../apps/api/src/rfq_workbench/integrations/ports.py)。

### 3.2 持久化出站意图，再向目标派发

1. 审批人点「请求同步」。后端校验角色、当前草案批准与来源，生成固定载荷、哈希、来源快照 ID、业务键和幂等键。出站意图与任务审计同事务提交，状态为 `PREPARED`。
2. 由「派发一次」或 [同步 Worker](../../scripts/sync_worker.py) 领取。派发前检查批准草案、来源快照、载荷完整性和目标预期版本，记录尝试、租约到期时间和 `lease_token`。真正的目标调用在工作台 SQLite 事务外执行，模拟外部状态也有独立的数据库。
3. 领取后再次检查租约持有者及派发条件，完成记录时也检查租约归属。过期的派发尝试进入 `UNKNOWN_OUTCOME`。这将进程中断后的恢复变成查询目标状态，而不是根据客户端是否收到响应来推测。
4. 正常回执将意图推进到 `ACKED`，保存目标 ID、版本和回执哈希。系统再按业务键确认只有一条目标记录，并读取目标内容，比较载荷字段，包括零件、版次、数量、币种、单价、总价和成本行。只有 `MATCH` 才首次成为 `VERIFIED`。目标缺失、差异或重复会留下对账结果。已核验意图保留历史状态，后续查到漂移会另记审计，所以判断目标当前内容时还要看最近一次对账和目标版本。
5. 同一询价的 500 件新草案批准后，意图从首次 `CREATE_DRAFT` 变成 `UPDATE_DRAFT`，使用原目标 ID 和预期目标版本。若目标已被改动，版本检查阻断覆盖。正常演示为目标版本 1 → 2。

实现见 [同步状态机](../../apps/api/src/rfq_workbench/sync.py)、[出站存储和审计](../../apps/api/src/rfq_workbench/sync_store.py)、[模拟系统](../../apps/api/src/rfq_workbench/integrations/fakes.py)。

### 3.3 哪些情况能重试

| 信号 | 当前处理 |
|---|---|
| 明确连接失败、`429`、适配器明确声明未处理的状态 | `RETRY_WAIT`。退避并考虑 `Retry-After`，再校验派发条件，受尝试上限约束 |
| 提交前后不明的超时、连接重置、无法证明未处理的响应、派发租约过期 | `UNKNOWN_OUTCOME`。先查幂等键与业务键。发现相同载荷就继续读回对账，发现差异或重复就保留结果。找不到记录时按适配器声明的一致性与等待窗口处理，满足条件才允许重新派发 |
| `409` / `412`、目标版本或载荷冲突 | `DIVERGED`，保留冲突与字段差异，等人工处理 |
| `400` / `422` | `REJECTED`，需要修正请求或映射 |
| `401` / `403`、尝试上限耗尽 | `QUARANTINED`，暂停自动派发，保留人工决议入口 |
| 当前批准失效、快照过期或前置条件变化 | `HELD` 或 `SUPERSEDED`，依据当前状态重建或结束旧意图 |

**提交后超时示例。** 模拟 ERP 把 100 件草案写入后抛出超时。工作台没有可用回执，进入「结果待确认」。审批人点「查询并对账」，系统以幂等键和业务键找到已提交记录，比较载荷，保存回执并读回，最终显示 `MATCH`。全程对应一条目标记录。现场步骤见 [[docs/05-面试与问答/09-选项B现场演示流程#3. 面试官点名时追加的演示]]。

### 3.4 版本、哈希和键各管什么

| 字段 | 保护的对象 |
|---|---|
| `expected_version` | 工作台任务状态，防止旧页面或旧识别结果覆盖当前状态 |
| `input_hash` / `reference_hash` | 计价输入、受控参考依据，支持识别过期草案 |
| `quote_hash` / `draft_version` | 审批对应的草案内容与版本 |
| `source_version` / TTL / `payload_sha256` | 上游快照时效和完整性 |
| HTTP `Idempotency-Key` | 已支持的工作台 POST 入口。按调用者、方法和路由定范围，并校验请求摘要。相同请求可在 24 小时内重用已完成响应，处理中提示查询，换内容复用同键会被拒绝。请求同步要求此请求头 |
| ERP `business_key` | 任务对应的目标对象身份，形如 `<run_id>:ERP`，改量前后保持相同 |
| ERP `x_idempotency_key` | 该次批准的出站写入。由任务、目标、操作、批准草案哈希与映射版本生成。相同写入尝试重用同一个键 |
| `expected_target_version` | 目标记录条件更新。目标已有并发改动时阻断旧更新 |

HTTP 幂等实现见 [工作台幂等](../../apps/api/src/rfq_workbench/idempotency.py)。目标端的防重依赖适配器实现幂等、版本条件与可靠查询。即使本地能恢复，真实 ERP 若没有等效能力，也需要重定验证方案和人工处理方式。

## 4. 怎么验证

| 证据 | 结果与口径 |
|---|---|
| [M7 本地验证](../../evals/results/m7/local.json) | 报价正常路径 4/4、预期阻断 8/8、知识 12/12、故障 6/6。覆盖的是冻结样例和规定条件 |
| [M7 在线识别](../../evals/results/m7/live.json) | 12 个文档包，153 个可见字段候选正确，其中 145 个文本验证，8 个正确视觉页仍需人工复核 |
| [M9 集成评测](../../evals/results/m9/local.json) | 17/17。受测场景里重复副作用、漏写、虚假确认、不安全派发均为 0。未知结果确认 5/5，注入差异检测 4/4。报告另计入一例为验证检测能力而注入的重复记录 |
| [冻结场景](../../evals/frozen/m9/scenarios.json) 与 [评测脚本](../../scripts/evaluate_m9.py) | 使用模拟系统、时钟和故障注入，覆盖提交后超时、派发中断、并发与目标差异。报告是项目保存的历史结果 |

评测里所谓“虚假确认”关注系统是否在目标状态未经验证时标记成功。面试时可用「对账通过」和「结果待确认」两个页面说明这个区别。样例和故障脚本能复现规定场景，生产可用性、恢复时间和端到端正确率仍需客户数据与目标系统验证。工程记录见 [[docs/03-实施与开发/08-工程决策/05-集成Harness]] 和 [[docs/03-实施与开发/09-阶段验收/11-M9集成Harness]]。

## 5. 现场追问与回答

| 面试官问 | 可直接回答 |
|---|---|
| “可靠”是不是指模型一定正确？ | “我们分开验证抽取和业务结果。字段要有支持它的来源，还要满足工程规则。视觉证据要人工确认。允许系统停在待复核，是为了让未满足条件的单子有明确下一步。” |
| 怎么证明没有重复写入？ | “我可以演示模拟 ERP 提交后超时。先查询原记录，再读回核对，最终目标只有一条。真实 ERP 需要验证同样的键、条件更新和查询能力，才能界定防重承诺。” |
| 两个人同时改草案会怎样？ | “工作台用任务版本拒绝旧操作。同步到目标时还有预期目标版本，两个系统各自保护自己的状态。” |
| 出站意图会不会一直挂住？ | “有限重试、租约恢复和对账能把中断归到可处理状态。持续不可达或数据冲突时会停住，保留错误、尝试和人工决议入口。原型可手动或由 Worker 执行这些步骤。” |
| 从模拟切换到客户生产前先验什么？ | “先拿获授权的真实样本和沙箱校验字段、单位、版本映射，再验证幂等键、查询可见性、并发写入与故障窗口。还要接上生产身份与权限、运行监控和告警，用客户样本重测正例、负例和延迟。” |
