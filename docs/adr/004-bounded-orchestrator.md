# ADR 004：有界任务调度与人工恢复

## 背景

M4 已能按按钮抽取、修正、计价与审批，但缺少明确的任务目的、统一补件提示及连续恢复入口。新增路由不能让审图、知识检索获得报价或审批权限，也不能复制一套与原任务状态不一致的流程数据库。

## 决定

使用 `orchestrator.py` 的显式分支和现有 SQLite `runs` JSON。新增 `orchestration` 元数据，保留意图、原始请求、创建角色、查询条件、暂停原因、结果快照。唯一业务状态仍是顶层 `state`，不引入第二个 workflow status 或新表；兼容 schema version 1 的旧任务。

选择 `prepare_quote`、`review_drawing`、`search_knowledge` 之一。文本仅作为上下文，不做关键词猜测或模型分类；未选择时持久化 `CLARIFICATION_REQUIRED`，用户选择后继续。目的确定后不可转换；需要转换时新建任务。

创建和补件不调用模型。一次显式 resume 最多执行一次抽取及一次计价或检索，没有 Agent 自由循环，没有自动审批。字段已存在时复用原提取与人工修正，再检查当前规则；缺文件要求补件，工程问题暂停，合法报价停在 `READY_FOR_APPROVAL`。检索和计价是有界同步节点，使用 `costed` 及其依据 hash 记录结果，不把瞬态 `RETRIEVING`/`COSTING` 另存为长期状态。

审图入口只要求图纸，不补造 RFQ 数量、币种或客户要求；检查图纸的九个字段、证据、批准版次和单模板适用性。输出问题、证据、审查范围限制；不做客户 RFQ 对照、完整 GD&T/孔位检查、定价或工程批准。旧计价、审批、导出 API 同样检查意图，防止绕过 UI。

知识查询结果保留为本次任务快照；未定意图任务和知识任务仅创建角色可读取及恢复。列表先过滤，越权详情返回 404。文件任务由工程师编辑、两角色读取、审批人审批；这里的 owner 是两个本地演示角色，不是企业用户 ID。角色改变时 UI 清空私有快照，忽略旧角色迟到的列表响应。

## 持久化与失效

每次写入通过原有乐观锁和 `BEGIN IMMEDIATE`，快照与事件在同一事务提交。模型调用仍在数据库事务外；抽取前先 CAS 认领，重复旧版本请求返回 409。等待人工补件/修正的任务重启后可恢复。执行中的进程崩溃与租约回收留给 M6，不宣称自动恢复所有中断。

资料和字段变化清除当前报价、审批、导出、任务结果与旧暂停说明，审计保留。参考依赖在恢复报价、审批、导出时重算 hash；变化使旧批准失效，需重新计算和审批。重复恢复已报价任务只校验新鲜度，不新建草案或撤销有效批准。完成的知识/审图任务重复恢复返回现有快照；重新审查需重抽取或更新资料，重新检索需新建查询任务。

## 影响与替代方案

没有新增运行依赖或数据库迁移；旧 `/runs` 分步操作继续保留。未采用 LangGraph，原因是当前三入口的同步有限路径可直接验证，暂不需要另一个调度框架。若以后替换内部实现，仍须保留单一权威状态、CAS、角色边界和幂等审批；不能同时维护两套状态机。

验证见 [[docs/acceptance-m5]] 与 `tests/test_orchestrator.py`；后续可靠性/集成内容见 roadmap M6。
